1. Legacy System Analysis

SVFRMS monitors a vertical farm. Each growing chamber holds one crop. The program simulates sensor readings (temperature, humidity, soil moisture, light, nutrient), compares them with the crop's acceptable ranges, raises alerts, switches on devices (cooling fan, water pump, ...) to correct the conditions, keeps water/energy totals, and at the end archives the alerts and writes a daily report to archive/daily_report.txt.

The whole system was one 393-line class, SVFRMS.java. Its main components were all static members of that class:

Component (legacy)What it did
ChamberThread ×420 cycles of random readings per chamber (CH1 Tomato, CH2 Strawberry, CH3 Lettuce, CH4 Chili)
processSensor()per-crop thresholds, alerts, water/energy accounting, device requests, all in one method
controlQueue + ControlThreadhand-written bounded queue (5) of "CH1|Cooling Fan" strings, consumed by activateControl()
handleEvent()string switch for logging, printing, alert storage and chamber summaries
archiveAlerts(), generateDailyReport(), saveArchiveReport()end-of-day archive, console report, file report

Baseline first. Before changing anything we built a characterization harness that drives the untouched legacy code with a fixed seed and hand-picked boundary readings. It records the console output, the sensor log and the archive file as golden files (1,423 lines). The refactored system must reproduce them byte-for-byte, which is our evidence that behaviour was preserved.

3. Proposed Design

Our goal was to keep every feature and output format exactly as it was while fixing the structure. The key decisions:

  • Split by responsibility into 14 packages and about 65 small classes. The largest is the composition root, and everything else is under 100 lines. No class mixes domain logic, I/O, threading and formatting. For example, ChamberMonitor (the new processSensor) only records the reading and runs the alert rules.
  • Crops are data, not code. A CropProfile record (ranges plus the water/energy cost of each breach) is loaded from crops.properties into a CropRegistry. One generic CropThresholdRule replaces all the per-crop blocks. Legacy quirks are kept as data. For example, only Tomato has a soil rule, so only Tomato has a soil.min line.
  • Events instead of a string switch. AlertService notifies listeners: a console printer, a summary tracker, a resource accountant, and a device responder. Each listener has one job.
  • Typed commands instead of "CH1|Cooling Fan". Device requests are ActivateDeviceCommand objects behind a ControlDispatcher interface, with a threaded queue for production and an immediate version for deterministic runs.
  • Dependency injection. Every class gets its collaborators through its constructor. FacilityAssembler is the single place where concrete classes are created and wired.

4. Final Architecture

The diagram shows the packages and how they talk. app wires everything. Chamber tasks publish readings, the monitor evaluates rules, and alerts fan out to listeners. Device requests go through the control queue, and reports are built from one immutable snapshot.

5. Extensibility and Maintainability

ChangeWhat you touch
Add a crop (Kale, Bell Pepper, Bok Choy, Eggplant)Add a block to crops.properties, or pass --crops file at runtime. 0 Java files. All four were added this way
Remove a cropDelete its block (or CropRegistry.remove). Chambers still get facility-wide checks
Grow a crop in a new chamberAdd CH5=Kale to a chambers file (--chambers)
Wire a device to an alertOne line in facility.properties, e.g. response.temperature.low=Heating Unit
New device / alert type / reportOne new class implementing Device / AlertRule / TemplateReport + one line in FacilityAssembler
New output (dashboard, SMS)Implement AlertListener or DeviceListener and register it
Real sensors instead of simulationImplement SensorSource. Nothing else changes

Maintainability comes from three things. Small classes have one reason to change. The golden tests fail on any accidental output change. The deterministic --seed N --sequential mode makes bugs reproducible. Brief features missing from the legacy code (Sensor Failure alert, alert severity, Heating/Ventilation/Shade devices, Weekly Crop, Water, Energy and Nutrient reports) are included, but they are opt-in or only triggered by new conditions, so the default output is still identical to the legacy output.
